@brightlocal/proposal — the shared proposal module (USE IT BY DEFAULT):

- AI INSIGHTS WORK: the working doc is registries/brightlocal/AI-INSIGHTS.md — the live-product captures (-1 Studios verbatim), the full aiInsights/foundation/visibility shape, locked decisions (text-varies-numbers-don't, arithmetic Location Score, per-action deep links, hub-and-spoke), the old↔new label map, screen ids, known gaps and next steps. Read it BEFORE touching AI Insights data, screens, or copy.

- For ANY hub, dashboard, or full-page screen with the app sidebar, import the shell and chrome from "@brightlocal/proposal" instead of composing GlobalLayout/Sidebar by hand or copying shell code into the screen:
  import { AppLayoutShell, ProposalSidebar, PageHeader, StatCard, HubStatCard, HubHeroCard, useProposalData } from "@brightlocal/proposal";
- EVERY compact metric tile is a <StatCard> (label/value/delta/tone/icon/info; metricKey binds from data.metrics; level="nested" for a stat row ON a bigger card). Never hand-roll Card + CardContent className="pt-6" for stats — BL's Card already pads content and pt-6 double-pads the top.
- The canonical page skeleton is:
  <SidebarProvider defaultOpen>
    <AppLayoutShell flush stickyHeader pinnedSidebar sidebarTone="white"
      sidebar={<ProposalSidebar />}
      header={<PageHeader breadcrumbs={[…]} title="…" meta={…} />}>
      <GlobalLayoutContentBody>…page content…</GlobalLayoutContentBody>
    </AppLayoutShell>
  </SidebarProvider>
  SidebarProvider and GlobalLayoutContentBody still come from "@brightlocal/ui-components".
- AppLayoutShell knobs are LITERAL props (the inspector edits them): flush, stickyHeader, pinnedSidebar, sidebarTone ("default" | "white" | "subtle" | "dark" | "brand"), sidebarFrame ("flush" | "floating" | "attached"), sidebarShadow, pageLayers ("default" | "raised"), navDensity ("compact" | "comfortable" | "expansive"), contentMaxWidth, tweaker.
- NAV DENSITY is variable-driven: the shell's scoped style consumes --gds-nav-font-size / --gds-nav-row-py / --gds-nav-sub-py / --gds-nav-sub-pl / --gds-nav-icon-size / --gds-nav-icon-stroke (compact defaults: 14px text, ~30px rows, subs left-aligned to the main label, 16px/stroke-1 icons). navDensity="comfortable" re-points them (roomier rows, 20px/1.5 icons); "expansive" mirrors the LIVE product nav (~48px rows, 15px labels, 20px icons). Also a tweaker row (Alt+T). Set the variables directly for per-screen fine-tuning.
- LOCKED VARIANT screens (A/B comparisons, hard-set client data): when the user asks for comparison screens or a screen pinned to specific data, hard-set the differing knobs as plain props AND set tweaker={false} so the screen is locked to its authored look (no Alt+T override layer). E.g. sidebarTone="brand" tweaker={false} vs sidebarTone="white" tweaker={false}; dataset="northside-dental" tweaker={false} pins the client.
- ProposalSidebar renders the proposal IA by default; pass `sections` only when a screen needs a different nav. Nav rows support `goto: "<screen name>"` and `transition` fields — flows live in the DATA, not in markup.
- ACTIVE NAV ROW: every screen states which page it is via activeId on the sidebar — <ProposalSidebar activeId="location-profile-hours" />. NAV MODEL v2: top-level rows are page LINKS (no accordions); a section's sub rows appear ONLY while the viewer is inside that section (activeId on it or a descendant). Subs are max ONE level — level-3 ids highlight their level-2 parent and level-3 content belongs ON the page (header tabs), not in the nav. Row ids are the section/sub ids in PROPOSAL_SECTIONS (e.g. "rankings-table", "location-profile-hours", "reviews"). Always set activeId on a screen that represents a specific page.
- TOP-LEVEL LANDINGS: every top-level nav item has a landing screen named exactly like its label ("AI Insights", "Rankings", "All Locations", ... — tagged section:"Top-Level Pages" in the share project), and the module's DEFAULT navLinks already wire every top-level row (and rankings-table) to them. Do NOT re-wire top-level navigation per screen; per-screen navLinks are for OVERRIDES and deep links only. Breadcrumb root is "All Locations" (goto: "All Locations"), then "Location Hub" for location-scoped pages.
- NAV GOTO LINKS are per-project DATA, not structure: data.navLinks maps row id → goto target (or { goto, transition }) and is applied to the default nav automatically. Wire flows by putting navLinks in the project's ProposalDataProvider data or dataset JSON rather than forking sections.
- GOTO BY ID (DEFAULT): a goto target should be "screen:<id>" — ids pin the exact screen and SURVIVE RENAMES; a bare screen name still resolves (case-insensitive) but breaks the day the screen is renamed, so names are only for hand-authoring when the id isn't known yet. When wiring by id, put the screen NAME in a trailing comment for readability (see the module's DEFAULT navLinks). Screen ids come from the Studio screens list / share URLs.
- HubStatCard / HubHeroCard accept `goto` / `transition` props for screen-to-screen links (they stamp data-grade-goto / data-grade-transition).
- LOCATION CARDS: <LocationCard location={l} goto="screen:dmrurue2wmp9u" /> renders one entry from data.locations. DATASET CARRY (snag 4 fix): entries may carry `dataset: "<name>"` — clicking the card stashes it session-wide (selectSessionDataset) BEFORE the goto, so the destination hub and every screen after render THE CLICKED location. - CARD GAP IS 16px EVERYWHERE CARDS MEET: grids of Cards (LocationCard, module cards, stat cards) use `gap-4`, and STACKED cards/sections on hub + feature pages use `space-y-4` (the At-a-Glance card sits 16px above the grid below it, same as the grid's own gaps — Ali, 22 Jul). Reserve `gap-6` for layout grids INSIDE a single Card and for toolbar→content rhythm; never for card-to-card spacing on any axis.
- BREADCRUMB DATA BINDING: a crumb can be `{ bind: "location", goto: "…" }` — PageHeader resolves the label from data.location.name at render, so location-scoped pages show the REAL location name in the trail. Location-scoped landings use [{ label: "All Locations", goto: "All Locations" }, { bind: "location", goto: "Location Hub - New Template" }].
- DATASET PROVENANCE: each lib/data/*.json carries a `provenance` map — dotted data paths → "brightlocal-source" (captured from the live product) | "proposed" (our enrichment/summarising). minus-one-studios mixes both (real scores/insights; proposed ledes, action labels, summaries, subMetrics); harbour-co and northside-dental are wholly proposed ("*"). Consult it before treating a number as real; mark new fields as you add them.
- ALL LOCATIONS LOOPS THE DATASETS: data.locations = datasetLocations() (one entry per lib/data/*.json — name/city/postcode/category/photo/phone from the dataset's `location` block, `dataset` = filename) + the legacy dirty-data entries. Adding a dataset file ADDS a clickable location; never hand-add a dataset-backed location.
- NAP DISCIPLINE: data.location is { name, address, phone, status } — `name` is the business NAME ONLY, never name-plus-address. Breadcrumbs bind the bare name; PageHeader's default meta composes `name — address` for display. Same rule for entries in data.locations. Never concatenate address or phone into a name field.
- Data comes from the proposal data seam: `useProposalData()` returns { account, user, location, keywords, aiInsights, foundation.*, visibility, competitors, metrics.* } with demo defaults; wrap a screen in <ProposalDataProvider data={{…partial…}} /> or name a dataset (<ProposalDataProvider dataset="harbour-co">) to re-skin the whole interface. NAMED DATASETS are raw JSON at registries/brightlocal/lib/data/<name>.json — partial patches deep-merged over the defaults (arrays replace wholesale). Merge order: defaults → dataset → data prop. Datasets: "harbour-co" (healthy scores), "northside-dental" (weak scores), "minus-one-studios" (REAL numbers captured from the live product's Location Summary page). Every dataset's location.status is "Active" — the only status VERIFIED on live; don't invent others. - PREFER DATA BINDING over hardcoded values: HubStatCard takes metricKey="reviews" (reads metric/delta/description from data.metrics.reviews); PageHeader's default meta is the current location; ProposalSidebar's Local Search Grid keyword rows come from data.keywords. Explicit props always win over bound values.
- SHAPE CONVENTION: each area of the product (rankings, reviews, citations, AI insights, …) gets its OWN top-level section in the data JSON — tables, keyword lists, insight items live under their area key, and screens bind with useProposalData().<area>. The data shape is SEPARATE from the nav structure — SECTIONS stay in the module; data never defines nav depth.
- AI INSIGHTS SHAPE (matched to the live product): aiInsights is { lastUpdated, updatesLeft, counts: { insights, recommendations }, tone, summaries: { concise|standard|detailed }, atAGlance: [3 strings], items: [{ id, area, areaLabel, severity, title, insight, recommendation, action, actions: [{ text, links?: [{ label, area? }] }] }] }. TEXT VARIES, NUMBERS DON'T: bind aiInsights.summary (the provider resolves summaries[tone]); switch voice with a one-key patch data={{ aiInsights: { tone: "concise" } }}; author text in summaries.<tone>, never in summary. areaLabel is the OLD-platform sidebar name ("Web Performance" ↔ "Website and content"); area is the nav row for drill-through; deep links live per-ACTION (a card's single CTA = first link across its actions). Screens compose the keys freely: hero = summary; compact card = title + action; full page = insight + recommendation + actions.
- LOCATION SCORE IS ARITHMETIC, NEVER AUTHORED: computeLocationScore(data) → { overall, foundation, visibility } from scoreModel weights (overall 50/50; foundation = Website 30 / GBP 30 / Reviews 20 / Citations 20; visibility = Maps 60 / Organic 40). The only authored numbers are foundation.<module>.score (+ subMetrics) and visibility.googleMaps/organic.score.
- HUB-AND-SPOKE (progressive disclosure): foundation.<module> cards on a summary/hub screen show the topline score and drill through their `area` via navLinks to the module's own page (Reviews, Citations, …); subMetrics bars belong on the drill-down page (or a deliberately dense management variant), not the hub.
- DON'T STARVE THE PAGE: the seam covers shared identity/area data, not every value on screen. For page-specific content the seam doesn't carry (table rows, chart series, one-off lists), invent rich realistic in-page data as usual — in-page constants are fine and explicit props always beat bound values. Never render a sparse or empty page because useProposalData() lacks a key; bind what exists, invent the rest.
- AppLayoutShell also takes dataset="<name>" (authored) and the ShellTweakerPanel has a Data row — Alt+T switches datasets live, session-only.
- Do NOT re-implement or inline copies of AppLayoutShell, ProposalSidebar, PageHeader, HubStatCard, HubHeroCard, or ShellTweakerPanel in a screen — the module is the single source of truth; screens that import it update automatically when it changes.
